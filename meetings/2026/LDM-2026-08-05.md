## Discussion

### C# 16 feature focus

Discussion: https://github.com/dotnet/csharplang/discussions/10276

We discussed where to focus our larger efforts during the C# 16 cycle. The previous two releases introduced substantial
features in extension members and unions. For C# 16, we think it is reasonable to concentrate on completing work already
underway and improving the experience around recent features, rather than requiring another feature of comparable size.

The proposed list is not intended to exclude smaller independent features. Those can still move forward when they are
useful and sufficiently well understood. The purpose of the list is to identify the larger, coherent areas where we
expect sustained design and implementation work.

#### Unsafe v2

The evolution of `unsafe` is already well underway and available in preview. Its rollout involves coordination across
the stack, and experience with the preview is likely to reveal places where the design needs further adjustment. We
therefore expect this to remain a significant focus in C# 16.

This work primarily benefits the safety and trustworthiness of low-level code rather than the day-to-day experience of
most C# developers. Today, some code that conceptually ought to be safe cannot be expressed in a way that lets the
language verify it as safe. The current `unsafe` work addresses part of that problem, but a fuller answer will require
better models for lifetimes and ownership.

We expect lifetime and ownership design to need a long lead time, as the current `unsafe` work did. We should begin
serious design exploration during this cycle and consider how language features and supporting APIs would be designed
together. This is forward-looking design work, not a commitment to ship an ownership or lifetime feature in C# 16.

#### Dictionary expressions

Dictionary expressions have been on our roadmap for several cycles and are close to completion. Collection expression
arguments supplied necessary groundwork, but the dictionary expression feature itself did not make C# 15. We believe
the design is substantially complete and should take it the rest of the way.

The next important step is to make the feature available under the preview flag. Real-world use may identify details
that require adjustment, but we do not expect major changes to the overall design.

#### Closed enums

Closed enums complete the exhaustiveness-oriented family introduced by unions and closed type hierarchies. Although
smaller than those features, they fill an important gap: enum values are frequently added over time, and developers
want the compiler to identify all the places that must be updated when the set of valid values changes.

We considered whether closed enums should compete afresh with unrelated feature proposals rather than being prioritized
because their related features have already shipped. The practical demand for exhaustive handling of enums, together
with the feature's expected size and its role in completing the broader exhaustiveness story, supports continuing the
work in C# 16.

#### Type inference improvements

Type inference is the main new focus area proposed for C# 16. Many follow-on ideas from unions would become more useful
if C# could infer type arguments from more information and in more language constructs. These improvements also have
broader applicability beyond unions.

We divided the opportunity into two broad categories. The first is inference from more context:

- The target type of an expression could contribute information about the result type of a generic method.
- Generic constraints could connect type parameters and allow one type argument to be inferred from another.
- The relationship between a union and its case types could participate in inference similarly to an inheritance
  relationship.

The second category is inference in more places. Generic type inference currently applies primarily to method calls. We
want to investigate applying it to constructor calls and type patterns as well. This would reduce the need for factory
methods whose only purpose is to obtain method type inference, and it would improve the symmetry between constructing a
generic value and consuming it in a pattern.

Our initial focus should be on improvements that do not add syntax. Partial type inference, where some type arguments
are written and others are explicitly left for inference, remains a recurring request. However, better inference from
targets, constraints, and union relationships may eliminate many of its motivating scenarios. We want to see how far
those improvements take us before adding a new partial-inference syntax.

Inference for generic extension members may also fit this area. In some cases the receiver supplies enough information
to infer the containing type's arguments even when the member's own type arguments must be written. We will first
develop a concrete proposal and evaluate its value and complexity alongside the other inference improvements.

Changes to inference can alter the binding of existing code, so compatibility must remain part of the design. Early
preview exposure will help us find those cases. An initial implementation of inference from constraints has already
shown that previously invalid calls can become valid; broader testing is needed to determine whether existing valid
calls can change meaning.

We also heard a concrete scenario in which inference from constraints enables a high-performance, LINQ-like library to
remain usable without exposing unwieldy generic signatures. That library is aimed at Native AOT scenarios where ordinary
LINQ can carry significant code-size costs. We will examine that scenario in a future meeting, both to
understand the immediate proposal and to ensure that a focused solution does not hinder a more general one later.

#### Declarative UI construction

We remain interested in improving C# for declarative UI construction, following our
[previous discussion](./LDM-2026-07-15.md#declarative-ui-construction). MVU-style frameworks repeatedly encounter
limitations in today's object construction syntax, and language improvements could make that programming model
substantially more usable.

This area is still exploratory. We do not yet know which programming model will ultimately be pursued or which language
features would best support it. We should continue collaborating on the exploration and use it to inform future language
design, but we do not consider declarative UI work a C# 16 delivery commitment.

#### Other areas

The focus list does not close the door on additional work. We revisited the longstanding gap between switch statements
and switch expressions. Existing proposals have explored both enhanced switch statement forms and return expressions.
The arrival of unions and broader exhaustiveness checking gives this area renewed
relevance: C# still lacks a statement-oriented form that provides exhaustiveness checking while allowing control flow
such as an early `return`. We will further develop the existing proposals and possible solutions in a future meeting.

We also expect useful, small features to continue progressing independently. A feature need not belong to one of the
larger focus areas if it fills a clear language gap and can be completed without distracting from those priorities.

#### Conclusion

We accept the proposed priorities. For C# 16, we will continue the `unsafe` evolution, finish dictionary expressions and
closed enums, and make syntax-free type inference improvements the principal new focus area. We will continue
declarative UI construction and lifetime or ownership work as forward-looking design explorations rather than C# 16
delivery commitments. This priority list does not exclude smaller independent features.
