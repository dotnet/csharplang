## Discussion

### Inference for pattern types

Champion issue: https://github.com/dotnet/csharplang/issues/9630  
Spec: https://github.com/dotnet/csharplang/pull/10352/changes/8d134f4e8a20f5f7508611577fab2a65d290e2c5

We continued our work on generic type inference by reviewing inference for types appearing in patterns. This complements
inference for constructor calls: we should be able to construct a generic case without repeating its type arguments, and
then consume it through pattern matching without repeating them either. The proposal builds on the target-typed inference
approach from our [previous discussion](./LDM-2026-10-05.md#target-typed-generic-type-inference).

The design reuses type-group lookup to find types with the given name, including generic types of different arities.
For unbound generic candidates, we attempt inference using the pattern's input type as a target type. We do not infer
from types or other information inside nested patterns or deconstruction subpatterns. After filtering for types that
are permitted in the pattern, we select a unique candidate, preferring a candidate that did not require inference.
We do not otherwise rank multiple successfully inferred candidates; the user must disambiguate those explicitly.

#### Generic and non-generic candidates

One concern we considered is the common .NET convention of giving generic and non-generic types the same name. When both
are valid candidates, the preference for the non-generic type prevents the generic type arguments from being inferred.
Interfaces make this particularly relevant because pattern compatibility does not require the two interfaces to have
an inheritance relationship.

Some common examples have mitigating factors. `IEnumerable` and `IEnumerable<T>` are in different namespaces.
`System.Collections.Generic`, but not `System.Collections`, is included in the SDK's implicit usings. The non-generic
interface therefore will often not be in scope. Non-generic factory types such as `ImmutableArray` are static and should
not be valid pattern candidates.

We considered whether syntax with omitted type arguments, such as angle brackets containing only commas, could let a user
request a generic candidate explicitly. We did not adopt such syntax today. We will continue thinking about the concern
and look for concrete scenarios where the existing candidate-selection rules are too limiting.

#### Compatibility and open questions

The existing distinction between an `is` type test and an `is` pattern remains relevant. The older type-test rules take
precedence when ordinary type lookup succeeds, and permit some tests that patterns reject, including certain tests that
are always false. Preserving that behavior can also prevent inference from being attempted when the old form ultimately
produces an error. We should investigate whether cases such as static types can fall through to pattern binding instead.

We also discussed removing the distinction more broadly to simplify the language. That would require investigating
existing code and assessing the compatibility impact. It is not a prerequisite for this proposal, though the new
inference scenarios may provide additional motivation to revisit it.

Type-group lookup itself has a potential breaking change, also identified for constructor inference: a generic type in
a nearer scope can stop lookup before it reaches a non-generic type in an outer scope that ordinary type lookup would
have found. We called out that this concern applies here as well.

The proposed inference direction is useful when the pattern type derives from, or otherwise implicitly converts to, the
input type. Patterns can also name a base type of the input type. We considered a fallback that would attempt inference
in the opposite direction, exchanging upper-bound and lower-bound inference, but left that as a possible extension rather
than adding it today. We also need to verify that nullable value-type inputs are unwrapped appropriately for inference.

Unions are an important motivating scenario, but inference through the union/case relationship requires the separate
proposal discussed next. These two features should compose without making the pattern proposal responsible for defining
that relationship.

#### Conclusion

We want this feature and will use the proposal as the basis for implementation work. The concerns above should be
recorded as open questions, investigated, and brought back as needed.

### Inference between union and case types

Champion issue: https://github.com/dotnet/csharplang/issues/10411  
Spec: https://github.com/dotnet/csharplang/pull/10355/changes/be29f8619cee907ffb69d4463b0169af481b6953

We reviewed extending inference to understand the relationship between a union and its case types. The existence of a
conversion does not automatically make that relationship available to type inference. Without this work, passing a
`Some<int>` to a method taking `Option<T>` does not infer `T` through the union relationship, nor can a target of
`Option<int>` supply the corresponding type argument to a method producing `Some<T>`.

The proposal adds rules to lower-bound and upper-bound inference. We look for a unique union case that matches the
other type, either directly or through that type's base types or implemented interfaces. For example, if `Option<T>` has
cases `None` and `Some<T>`, a `Some<int>` argument matches only the `Some<T>` case. We then perform lower-bound inference
from `Some<int>` to `Some<T>`, inferring `T` as `int`, rather than attempting inference directly against `Option<T>`.

If multiple cases could match, we do not attempt to choose between them, even if those cases have an inheritance
relationship. For example, cases involving both `IEnumerable<T>` and `IReadOnlyCollection<T>` can leave more than one
possibility.

Recursing through the case type, rather than treating the case as simply deriving from the union, is important for
variance. A case may itself be a variant interface, and inference needs to respect that interface's variance rather
than use the union's lack of variance. The specification wording follows the existing inheritance-related inference
rules, though we acknowledged that this makes it difficult to read.

As with other inference improvements, additional bounds can change inference results, make previously inapplicable
overloads applicable, or introduce ambiguities. We recognized that potential compatibility impact.

We spent some time on the interaction with user-defined conversions. Union conversions currently take a back seat to
user-defined conversions, in part to support existing types adopting the custom-union pattern while retaining their
conversion operators for older consumers. Inference could therefore succeed through the union/case relationship, while
the eventual conversion uses a user-defined operator instead.

One view was that these are properly separate operations: inference establishes type arguments from a known
relationship, without specifying which conversion must subsequently execute. We also considered changing conversion
precedence or suppressing inference in the presence of a user-defined conversion. Neither seemed necessary to proceed.
Existing operators will often implement the same behavior as the union conversion anyway, though that is not guaranteed.

#### Conclusion

We will include this proposal in the inference work for now. We will leave conversion precedence unchanged and watch for
concrete problems with the interaction between inference and user-defined conversions.

### Final initializers

Champion issue: https://github.com/dotnet/csharplang/issues/10033  
Old Spec: https://github.com/dotnet/csharplang/blob/5055b97eee8c10d12f822f6d4db9464329615947/proposals/final-initializers.md  
Proposal reboot: https://github.com/dotnet/csharplang/pull/10360/changes/e289b8b011a9119390e67f0d6eff619a9c262f19

We returned to final initializers with a revised proposal. Today's goal was to revisit the motivation and get a read on
whether the feature is worth pursuing, not to approve the detailed design.

#### Motivating scenarios

Object initializers and `with` expressions allow initialization to continue after constructors have finished, but there
is no corresponding hook for the type author to run code after those operations. Final initializers would provide that
hook for validation, normalization, and computation of cached state. They would run for object creation even when no
object initializer is written, and after the updates in a `with` expression.

We reviewed examples where properties must be considered together. For a range with `Min` and `Max`, validating each
assignment individually can reject a valid final result because an intermediate state is invalid. The same issue arises
when a `with` expression changes both endpoints of an existing range. Required members ensure that assignments occur,
but do not tell an accessor that all the other assignments have finished.

Cached state presents a related problem. A record can compute a full name or a lookup dictionary during construction,
only for a `with` expression to change the source properties while leaving the copied cache stale. Recomputing in a
final initializer would give the type author a single place to restore consistency. This would recompute the cache
even when the particular source property did not change; the proposed hook does not track which members were updated.

Moving this logic into individual accessors introduces boilerplate, can repeat expensive work, and may require abandoning
the concise positional-record form. A shared recomputation helper also cannot ordinarily assign `readonly` fields.
Final initializers would be allowed to assign `readonly` fields and init-only properties as part of initialization.
Other potential uses include starting change tracking or freezing an object after its initial setup. They also provide
a place to call virtual members after all constructors in the hierarchy have completed.

#### Implementation and compatibility

The reboot proposes a pay-for-play model: only types with final initializers need the corresponding methods and calls.
Ordinary user code would not be able to invoke a final initializer later and thereby overwrite `readonly` state.
Serializers would need a way to participate in the initialization protocol.

Under this approach, adding a final initializer to an existing type is a breaking change. Already compiled consumers
will not contain the new call, so code moved into the final initializer may not execute. Older compilers would need
to be blocked from constructing types that have final initializers, with required members providing relevant precedent.
We noted that the runtime cannot reconstruct the end of a C# object initializer from existing IL, though it could
potentially detect and reject construction that omits a required final-initializer call.

We were concerned that adding an `init` block inside a type looks like a private implementation change, despite imposing
a new requirement on callers. We considered whether a marker in the type declaration could make that public contract
more apparent. Another view was that this is comparable to existing versioning concerns, including adding required
members, and can be managed as part of a library's compatibility policy.

Record inheritance presents an additional tradeoff. A `with` expression whose static receiver type is a base record
must still run the final initializer of the actual derived record. To avoid checks for types that do not participate,
the reboot proposes that a derived record cannot introduce a final initializer unless its base record already has one.
That would also prevent older callers from bypassing a derived initializer through the base type.

We worried that this restriction would require library authors to anticipate future needs and add empty final
initializers throughout their record hierarchies. It could also constrain future factory-method designs where the
caller continues initializing an object without knowing its exact runtime type. Alternatives included synthesizing
stubs for records or revisiting the original idea of a virtual hook on `object`, with runtime optimization of empty
calls. We should consult the runtime team before ruling out a less restrictive implementation. None of these
implementation choices was settled today.

#### Scope and prioritization

There was support for focusing the feature on immutable objects that use piecewise initialization. Mutable objects
still need to cope with subsequent changes and intermediate states throughout their lifetime. We also noted that
serialization remains an important scenario and that nullable analysis needs further design.

The examples were motivating, but we did not all agree that the feature should take priority over other work. Some
uncertainty concerned available implementation resources rather than the usefulness of the idea; another concern was
whether the existing limitations were significant enough to justify the feature. Any commitment would need to follow
broader triage against competing proposals. Given current resources, this would be work for after C# 16, not an addition
to the current release plan.

#### Conclusion

There is some preference in favor of the feature, alongside uncertainty about whether it is worth pursuing and some
opposition. We have not placed it in the working set at this point. We will return to it during broader triage;
exploration of the design and implementation questions can continue in the meantime.
