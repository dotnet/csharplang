## Discussion

### Type parameter inference for constructor calls

Champion issues:

- https://github.com/dotnet/csharplang/issues/9626
- https://github.com/dotnet/csharplang/issues/9627

We reviewed progress on target-typed generic inference and constructor type inference, which we
[previously placed](../2025/LDM-2025-08-20.md#target-type-inference-improvements) in the working set. This was an
opportunity to adjust the direction of the work rather than a request for final approval.

#### Generalized generic type inference

Champion issue: https://github.com/dotnet/csharplang/issues/9626  
Proposal: https://github.com/dotnet/csharplang/blob/ed20eea13c0e655b907e8a8054553ecee62eb0aa/proposals/generalized-type-inference.md  
Proposal PR: https://github.com/dotnet/csharplang/pull/10311

We liked unifying the inference machinery across methods, constructors, and potential future consumers rather than
creating separate algorithms. The construct-neutral refactoring is intended to be behavior-preserving on its own.

The open problem is defining where target types come from. The specification currently models target-typed constructs
through conversions specific to each construct, while the compiler often binds an expression before applying its target
conversion. Generic inference needs the target type during binding. Both the specification and the compiler may
therefore require restructuring so that target-derived inference is available at the appropriate time and behaves
consistently.

Target-derived bounds are an intentional semantic change and can affect applicability, inferred types, ambiguity, and
overload selection. The precise target-typing model and `ref` compatibility rules remain open.

#### Type groups

Champion issue: none dedicated; tracked provisionally under https://github.com/dotnet/csharplang/issues/9627  
Proposal: https://github.com/dotnet/csharplang/blob/89597274f4c00a3031aac9d17f5f123d76150de2/proposals/type-groups.md  
Proposal PR: https://github.com/dotnet/csharplang/pull/10310

Stopping at the first scope with a non-empty result creates a compatibility concern. A nearer declaration of any arity
can hide a more distant declaration that today's arity-specific lookup would find. A namespace, type parameter, or alias
for a constructed type is a blocking result: it stops lookup at that scope without forming a type group. Fully
qualifying or aliasing the intended type can sometimes recover the old meaning, but those remedies may be cumbersome and
do not address every later ambiguity between members of a group. We want to start from a simple and coherent lookup
model, then prototype it against real code to measure the nature and frequency of breaks before adding compatibility
rules.

We also discussed common framework patterns that place generic and non-generic types side by side, such as the static
`Vector128` class and `Vector128<T>`, or `System.Numerics.Complex` and `System.Numerics.Complex<T>`. For constructible
pairs such as the latter, existing overload-resolution tie-breakers may preserve the non-generic result in many cases.
We also considered whether a mechanism similar to overload resolution priority could help disambiguate such cases.
However, built-in numeric types that lack a literal suffix, such as `byte` and `short`, cannot be pinned by a literal's
natural type and need specific investigation.

For nested generic types, the current draft permits inference only for the innermost name. An example showing inference
for both the containing and nested types was provided, but we still need motivating scenarios for why that behavior
would be useful before deciding whether omitted type arguments should also be inferred for containing types.

#### Constructor type inference

Champion issue: https://github.com/dotnet/csharplang/issues/9627  
Proposal: https://github.com/dotnet/csharplang/blob/554d4f43226564cf9991a7dcb6561f0c87f4637a/proposals/inference-for-constructor-calls.md  
Proposal PR: https://github.com/dotnet/csharplang/pull/10312

The draft forms one candidate set from the constructors of every type in the group, retaining those for which inference
succeeds and that are applicable. We discussed instead trying the non-generic type first and using inference only as a
fallback. That would avoid most breaking changes, but would make non-generic types special and could prevent a better
generic constructor from winning. We preferred to prototype the simpler combined model first and use compatibility data
to determine whether another rule is necessary.

For object creation with dynamic arguments, the name before the argument list must still resolve to a single type.
Otherwise, the expression is an error. This avoids implementing the new type inference behavior in the runtime binder.

The most important compatibility cases arise when a generic type adds an applicable constructor beside a non-generic
type. The new candidate can win overload resolution or make the call ambiguous. We need to identify realistic examples
and provide a practical way to request the zero-arity type when inference is not desired. An explicit target type or
cast may disambiguate some calls. We also briefly considered syntactic escape mechanisms, including an `@` prefix, an
empty type argument list, or a discard in the type argument list, but did not select an approach.

#### Conclusion

We did not approve the proposals or settle their compatibility questions. The next work is to prototype the design,
compare the specification with existing compiler behavior, collect real-world breaks, and investigate disambiguation of
the non-generic case. Work on type inference for type patterns is expected to proceed before the larger effort to
establish a general target-typing model.
