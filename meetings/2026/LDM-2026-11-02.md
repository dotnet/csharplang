## Discussion

### Working set triage

We reviewed the working set to focus on proposals receiving active design or implementation attention. Moving a proposal
to the backlog does not mean we no longer want it; it means we are not currently making active progress on it.

- [#1502: Ideas for working with fixed buffers](https://github.com/dotnet/csharplang/issues/1502): We will close this
  grab bag of ideas; anyone interested in pursuing an individual idea should open a separate proposal.
- [#7047: Method attribute target for record primary constructors](https://github.com/dotnet/csharplang/issues/7047):
  This was implemented in C# 12, so we will move it to the `12.0` milestone.
- [#8610: Block-bodied switch expression arms](https://github.com/dotnet/csharplang/issues/8610): We still see value in
  this, but it has not made enough progress to remain in the working set. We will move it to the backlog.
- [#8611: Enhanced switch statements](https://github.com/dotnet/csharplang/issues/8611): This shares the motivations and
  lack of progress of the related switch-expression work. We will move it to the backlog.
- [#9243: Expression blocks](https://github.com/dotnet/csharplang/issues/9243): This is part of the same group of
  switch-related proposals and has not been actively advancing. We will move it to the backlog.
- [#8613: User-defined positional patterns](https://github.com/dotnet/csharplang/issues/8613): We still see potential in
  active patterns, but have not encountered sufficiently pressing scenarios to prioritize them. We will move this to the
  backlog.
- [#8622: Variable declarations under disjunctive patterns](https://github.com/dotnet/csharplang/issues/8622): The
  previous design did not resolve our concerns, and implementation may require significant compiler architecture changes.
  We will move this to the backlog until a new design addresses the concerns.
- [#8659: Dictionary expressions](https://github.com/dotnet/csharplang/issues/8659): This is actively being implemented
  and completes an important part of the collection expression story. It remains in the working set.
- [#8848: Top-level type accessibility](https://github.com/dotnet/csharplang/issues/8848): We agree there is a problem
  with controlling visibility to friend assemblies, but do not agree on the proposed solution. We will move this to the
  backlog.
- [#8865: Breaking change warnings](https://github.com/dotnet/csharplang/issues/8865): We have taken a more ad hoc
  approach to managing breaking changes and no longer think this general warning mechanism is necessary. We will close
  the issue.
- [#8879: Type classes](https://github.com/dotnet/csharplang/issues/8879): This issue does not contain a concrete
  proposal we would pursue, and extension interface implementation is tracked separately. We will close it.
- [#9319: Extension interface implementation](https://github.com/dotnet/csharplang/issues/9319): We will champion the
  existing proposal and move it to the backlog.
- [#8928: Type unions](https://github.com/dotnet/csharplang/issues/8928): C# 15 includes type unions, but case
  declarations and standard unions were not completed as part of this work. We will move the umbrella issue to the
  `15.0` milestone and document what was and was not done.
- [#9001: Async method exception filter](https://github.com/dotnet/csharplang/issues/9001): We have seen little interest
  or traction for this proposal, so we will close it.
- [#9009: Collection expressions for non-enumerable types](https://github.com/dotnet/csharplang/issues/9009): Relaxing
  the requirements could address real scenarios, but it is not currently a priority. We will move it to the backlog.
- [#9011: Closed enums](https://github.com/dotnet/csharplang/issues/9011): This is on the active schedule and remains in
  the working set.
- [#9031: `fieldof()`](https://github.com/dotnet/csharplang/issues/9031): We recognize the underlying source generator
  scenarios, but are skeptical of exposing a backing field that the property is intended to encapsulate. We will close
  the issue.
- [#9046: Interpolated string handler method names](https://github.com/dotnet/csharplang/issues/9046): Although the
  proposal addresses duplicated handler code, we no longer think the problem is important enough to pursue. We will close
  the issue.
- [#9123: Static abstract interfaces and static classes](https://github.com/dotnet/csharplang/issues/9123): Allowing
  static classes to implement interfaces could be useful, but there are design questions to resolve. We will move this
  to the backlog.
- [#9119: `params in` parameters](https://github.com/dotnet/csharplang/issues/9119): We do not know of a current runtime
  team need, and existing alternatives reduce the urgency. We will close this unless a concrete need emerges.
- [#9138: Target-typed static member access](https://github.com/dotnet/csharplang/issues/9138): This is being actively
  considered alongside related features, so it remains in the working set.
- [#9453: Type parameter inference from constraints](https://github.com/dotnet/csharplang/issues/9453): This is part of
  the active inference work and remains in the working set.
- [#9626: Target-typed generic type inference](https://github.com/dotnet/csharplang/issues/9626): This is part of the
  active inference work and remains in the working set.
- [#9627: Target-typed inference for constructor calls](https://github.com/dotnet/csharplang/issues/9627): This is part
  of the active inference work and remains in the working set.
- [#9500: Case declarations](https://github.com/dotnet/csharplang/issues/9500): We will leave this in the working set
  for now and defer its final triage until the upcoming discussion of discriminated unions and related proposals.
- [#9565: Standard unions](https://github.com/dotnet/csharplang/issues/9565): Standard unions remain a potential library
  concern, but we are no longer pursuing related language work. We will close this issue.
